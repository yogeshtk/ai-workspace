App Anatomy: File → Job

When you open an unfamiliar Spring Boot + Docker repo, use this to find your bearings. Print it, pin it, come back to it.

The two worlds

Every one of these repos stacks two separate concerns. Keep them mentally separate — most confusion comes from mixing them up.

WorldQuestion it answersOwned by
Application worldWhat does the app do?Java + Spring Boot
Packaging/runtime worldHow does the app run, and alongside what?Docker

Application world — file → job

File / folderJob
pom.xml or build.gradleDeclares dependencies (which libraries the app uses) and how to build the app into a runnable artifact.
src/main/java/.../*Application.javaThe entry point — the class with @SpringBootApplication and a main method. Starting here tells you the app's root package.
src/main/java/.../controller/Handles incoming HTTP requests. Receives, delegates, returns a response. Should hold no business logic.
src/main/java/.../service/Business logic lives here. The "what should happen" layer, called by controllers.
src/main/java/.../repository/Talks to the database. CRUD operations only — no business logic.
src/main/resources/application.yml or .propertiesConfiguration — database URLs, ports, feature flags, per-environment values. Read this before assuming a value is hardcoded.
src/test/Tests, mirroring the src/main package structure.

Packaging/runtime world — file → job

File / folderJob
DockerfileRecipe for turning the built app (usually a JAR) into a Docker image — a portable, runnable snapshot.
docker-compose.ymlDescribes a whole running system — this app's image plus its dependencies (database, cache, message queue), how they network together, and what ports are exposed.
.dockerignoreFiles excluded when building the image (keeps it small, avoids leaking secrets/build artifacts).
(built) JAR file, usually under target/ or build/libs/The compiled, runnable app — what the Dockerfile copies into the image. Not committed to git; regenerated by the build.

The pipeline, end to end

Java source → build tool (Maven/Gradle) compiles it → packaged as a runnable JAR → Dockerfile copies that JAR into an image → docker compose up (or docker run) starts a container from that image → the running container is your app.

Core vocabulary

TermDefinition
ImageA built, versioned snapshot of everything the app needs to run. Doesn't run by itself.
ContainerA running instance of an image. You can have several containers from one image.
BeanAn object Spring creates and manages for you (instead of you writing new). Controllers, services, and repositories are typically beans.
Auto-configurationSpring Boot's mechanism for wiring up beans automatically based on what's on the classpath and in config — the reason there's little boilerplate compared to plain Spring.
