Lesson 1 · Orientation

The Map: What You're Looking At

When you open your new team's repo for the first time, you'll see a pile of unfamiliar files. This lesson gives you the map before you need it — so nothing you see in week one looks random.

Here's the situation this is built for: you're about to be handed access to an existing Spring Boot application that runs in Docker. You didn't write it. Your first job isn't to change it — it's to find your way around it. That starts with knowing what each file in the repo is for, before you read a single line of logic.

Two worlds, stacked together

Every repo like this stacks two separate concerns on top of each other. Keeping them mentally separate is the single highest-leverage habit for navigating one of these codebases:

  • The application world — Java + Spring Boot. Answers: what does the app do?
  • The packaging/runtime world — Docker. Answers: how does the app run, and alongside what?

A bug in "what does the app do" is a Java/Spring Boot problem. A bug in "why won't it even start" or "why can't it reach the database" is very often a Docker problem. Half of navigating confidently is correctly sorting a question into one bucket or the other before you start digging.

The application world, file by file

A typical Spring Boot project looks like this (simplified):

src/
  main/
    java/com/example/app/
      AppApplication.java       ← the entry point
      controller/
        OrderController.java
      service/
        OrderService.java
      repository/
        OrderRepository.java
    resources/
      application.yml           ← configuration
pom.xml                          ← dependencies + build instructions

Three things worth fixing in memory right now:

  • AppApplication.java — the class annotated @SpringBootApplication, with the main method. This is where the app starts. It's usually short and mostly empty — Spring Boot's whole design goal is that this file stays boring.
  • The controller / service / repository split — a convention (not enforced by the language) for where a given kind of code lives. Controllers receive HTTP requests. Services hold business logic. Repositories talk to the database. You'll use this constantly once you start tracing requests through the code, in a later lesson.
  • application.yml — externalized configuration. Database URLs, ports, feature flags. If a value looks hardcoded in Java but you'd expect it to change per environment, check here first — it's probably not hardcoded, it's read from this file.

The packaging/runtime world, file by file

Alongside the Java code, you'll find Docker-specific files:

Dockerfile           ← recipe: turn the built app into an image
docker-compose.yml    ← recipe: run this image + its dependencies together

Two terms to pin down precisely, because people use them loosely and it causes real confusion:

  • Image — a built, versioned snapshot of the app and everything it needs to run. An image doesn't run by itself — it's a blueprint.
  • Container — a running instance of an image. When someone says "the container crashed," they mean a running instance stopped unexpectedly — the image itself is fine.

A docker-compose.yml usually describes more than just your app — often a database container and maybe a cache or message queue too, wired together on a shared network. That's the "system" your one app is actually part of.

The whole pipeline, end to end

Here's how the two worlds connect, in order:

  1. You (or a teammate) write Java source code.
  2. The build tool (Maven, reading pom.xml) compiles it and packages it as a runnable JAR file.
  3. The Dockerfile says: "take that JAR, copy it into an image."
  4. docker compose up starts a container from that image — and any other containers the compose file describes (like a database).
  5. The running container is your app, as far as the outside world is concerned.
Tangible win Given any Spring Boot + Docker repo, you can now point at a file and say which of the two worlds it belongs to, and roughly what job it does — before reading a line of its contents.

Check your recall

Where would you expect to find the port number the app listens on?

A teammate says "the container keeps crashing." What just failed?
